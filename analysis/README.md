# Analysis Notebooks

말해봄 서비스의 음성 답변 분석 기능을 구현하기 위해 진행한 데이터 분석 및 실험용 Colab Notebook 모음입니다.

본 폴더는 수급자의 음성 답변을 STT로 변환한 뒤, 전처리된 발화 텍스트와 음성 정보를 활용해 인지검사 응답 분석 지표를 산출하는 과정을 정리합니다.

분석 실험은 다음 흐름을 중심으로 진행했습니다.

```text
음성 답변
→ STT 변환
→ STT 텍스트 전처리
→ 반응 시간 / 반복어 비율 / 답변 길이 산출
→ LLM 기반 화행 적절성 평가
→ 문항별 분석 결과 저장 및 리포트 활용
```

---

## 프로젝트 내 역할

본 분석 폴더는 팀 프로젝트 중 데이터 분석 및 발화 평가 로직 설계 과정에서 수행한 작업을 정리한 공간입니다.

주요 작업 범위는 다음과 같습니다.

* 고령층 음성 데이터 구조 확인 및 STT 적용 가능성 검토
* Hugging Face 기반 Whisper 계열 STT 모델 테스트
* STT 결과 텍스트의 잡음 표기, 라벨성 표기, 불필요한 공백 제거 전처리
* 반응 시간, 반복어 비율, 답변 길이 등 발화 분석 지표 산출 방식 구현
* 문항 유형별 답변 길이 점수 기준 설계 및 테스트
* LLM 기반 화행 적절성 평가 프롬프트 설계 및 테스트
* 인지검사/인지훈련 문항 데이터 분할 및 DB 연동 테스트
* 분석 로직을 백엔드 연동용 Python 파이프라인으로 정리하기 전 단계의 실험 수행

## 분석 목표

말하기형 인지검사는 단순히 정답 여부만 확인하는 것이 아니라, 수급자가 질문을 듣고 얼마나 자연스럽게 반응하고, 문항 의도에 맞게 답변했는지를 함께 확인해야 합니다.

이를 위해 본 프로젝트에서는 다음 분석 항목을 활용했습니다.

| 분석 항목       | 설명                             |
| ----------- | ------------------------------ |
| STT 변환      | 수급자의 음성 답변을 텍스트로 변환            |
| STT 텍스트 전처리 | 잡음 표기, 라벨성 표기, 불필요한 공백 등을 제거   |
| 반응 시간       | 문항 제시 후 첫 발화가 시작되기까지 걸린 시간     |

| 답변 길이       | 채움 표현, 공백, 문장부호를 제외한 의미 글자 수   |
| 화행 적절성 점수   | 문항 유형과 답변 내용의 적절성을 LLM 기반으로 평가 |

## 분석 파이프라인

### 1. STT 적용 가능성 검토

고령층 음성 데이터와 라벨링 JSON 파일을 확인하고, 음성 파일과 전사 텍스트를 매칭했습니다.

주요 작업은 다음과 같습니다.

* 데이터 폴더 구조 확인
* WAV 음성 파일과 JSON 라벨 파일 개수 확인
* JSON의 `fileNm`과 실제 WAV 파일명 매칭
* 유니코드 정규화를 통한 한글 파일명 매칭 오류 보정
* 지역, 나이, 성별, 대화 주제, 정답 전사 텍스트 확인
* Hugging Face 기반 Whisper 계열 STT 모델 적용 테스트

STT 모델 테스트는 실제 서비스에서 사용자의 음성 답변을 텍스트로 변환할 수 있는지 확인하기 위한 사전 실험으로 진행했습니다.

---

### 2. STT 텍스트 전처리

STT 결과에는 실제 답변 내용 외에도 잡음, 침묵, 웃음, 기침 등 분석에 불필요한 표기가 포함될 수 있습니다.

이를 최소한으로 정리하기 위해 전처리 함수를 작성했습니다.

전처리 기준은 다음과 같습니다.

* `(NO:)`, `[NO:]`, `<NO:>` 등 라벨성 표기 제거
* `(웃음)`, `[기침]`, `<소음>` 등 비언어·잡음 표기 제거
* 괄호 없이 들어오는 `NO:` 표기 제거
* 줄바꿈, 탭, 여러 공백 정리
* 양끝 따옴표 제거
* 답변의 의미를 바꾸는 수정은 하지 않음

전처리는 이후 반복어 비율, 답변 길이, LLM 평가에 입력되는 텍스트 품질을 맞추기 위한 단계입니다.

---

### 3. 반응 시간 측정

반응 시간은 문항이 제시된 뒤 수급자가 실제로 발화를 시작하기까지 걸린 시간을 의미합니다.

실험 노트북에서는 음성 파일에서 처음 소리가 감지되는 시점을 계산하는 방식으로 반응 시간을 측정했습니다.

주요 방식은 다음과 같습니다.

* `librosa`로 음성 파일 로드
* 일정 길이의 프레임 단위로 음성 크기 계산
* 전체 최대 음량 대비 기준값 설정
* 기준 이상 소리가 일정 시간 이상 지속되면 첫 발화로 판단
* 첫 소리 감지 시점을 초 단위로 반환

이 실험은 실제 서비스에서 TTS 문항 종료 시점과 사용자의 답변 시작 시점을 연결해 반응 시간을 산출하기 위한 기초 로직입니다.

---

### 4. 반복어 비율 계산

반복어 비율은 같은 어절이 바로 연속해서 반복되는 비율로 정의했습니다.

예시는 다음과 같습니다.

```text
"어 어 그 뭐냐 물 주문해브러"
→ "어"가 연속 반복됨
```

계산 방식은 다음과 같습니다.

1. 문장부호 제거
2. 공백 기준 어절 분리
3. 바로 앞 어절과 같은 어절이 반복되는 경우 카운트
4. 반복 어절 수를 전체 어절 수로 나누어 비율 계산
5. 반복어 비율을 0~100점으로 변환

점수 기준은 다음과 같이 설정했습니다.

| 반복어 비율 |  점수 |
| -----: | --: |
|  5% 이하 | 100 |
| 15% 이하 |  80 |
| 30% 이하 |  60 |
| 50% 이하 |  40 |
| 50% 초과 |   0 |

이 지표는 발화 중 같은 표현이 과도하게 반복되는지를 확인하기 위한 보조 지표입니다.

---

### 5. 답변 길이 산출

답변 길이는 단순 문장 수가 아니라, 채움 표현과 불필요한 기호를 제외한 의미 글자 수로 계산했습니다.

길이 계산에서 제외한 요소는 다음과 같습니다.

* `음`, `으음`, `어어` 등 단독 채움 표현
* `그 뭐냐`, `그 뭐지`, `뭐라고 해야 하나` 등 구 단위 채움 표현
* 공백
* 문장부호
* 따옴표와 괄호류 기호

문항 유형에 따라 적절한 답변 길이가 다르기 때문에, 모든 문항에 같은 기준을 적용하지 않았습니다.

예를 들어 `오늘 날짜 말하기`는 짧게 답해도 정상일 수 있고, `추억 말하기`는 구체적인 회상이 필요하므로 상대적으로 긴 답변을 기대했습니다.

문항 유형별로 답변 길이 점수 기준을 다르게 설정한 이유는 다음과 같습니다.

| 문항 유형      | 길이 기준 설정 이유        |
| ---------- | ------------------ |
| 오늘 날짜 말하기  | 날짜·요일 등 짧은 답변도 정상  |
| 규칙 기반 언어추론 | 공통점만 짧게 말해도 정답 가능  |
| 상황 질문 답하기  | 행동이 드러나면 짧아도 의미 있음 |
| 그림 설명하기    | 인물·사물·행동 묘사가 필요    |
| 추억 말하기     | 구체적 회상 발화가 필요      |

---

### 6. LLM 기반 화행 적절성 평가

화행 적절성 점수는 답변이 문항의 의도에 맞게 수행되었는지를 평가하는 항목입니다.

LLM 평가 프롬프트는 문항 유형별로 다르게 설계했습니다.

평가 대상 문항 유형은 다음과 같습니다.

* 오늘 날짜 말하기
* 그림 설명하기
* 상황 질문 답하기
* 규칙 기반 언어추론
* 추억 말하기

각 프롬프트는 다음 기준을 포함하도록 작성했습니다.

* 문항 의도 정의
* 답변에서 확인해야 할 요소
* 0, 40, 60, 80, 100점 기준
* 애매한 답변에 대한 경계 규칙
* STT 오류나 고령자 구어체를 고려한 판정 기준
* 출력 형식 제한

LLM 출력은 반드시 다음 점수 중 하나만 반환하도록 제한했습니다.

```text
0, 40, 60, 80, 100
```

이후 테스트 케이스를 통해 예상 점수와 LLM 출력 점수를 비교하며 프롬프트 동작을 확인했습니다.

---

### 7. 문항 데이터 분할

인지검사와 인지훈련에 사용할 문항 데이터를 검사 목적과 훈련 목적에 맞게 분할했습니다.

분할 기준은 다음과 같습니다.

* 전체 문항을 문항 유형별로 그룹화
* 각 문항 유형 내부에서 하위분류 비율 유지
* 검사 문항과 훈련 문항을 3:7 비율로 분리
* 무작위 분할 시 재현성을 위해 seed 고정
* 분할 결과를 JSON 파일로 저장

생성 파일 예시는 다음과 같습니다.

```text
questions_split_3_7.json
questions_test.json
questions_train.json
```

이 과정은 문항 유형과 하위분류가 한쪽에 치우치지 않도록 하기 위한 작업입니다.

---

### 8. 문항 데이터 DB 연동 테스트

분할된 문항 데이터를 서비스 DB에 저장하기 위한 연동 테스트를 진행했습니다.

주요 작업은 다음과 같습니다.

* JSON 문항 파일 로드
* 필수 필드 존재 여부 확인
* DB 연결 테스트
* 기존 문항 수 확인 후 중복 삽입 방지
* `QUESTIONS` 테이블에 문항 데이터 삽입
* `QUESTION_TYPES` 테이블에 문항 유형별 화행 적절성 평가 기준 업데이트

DB 연동 테스트는 실제 서비스에서 문항을 조회하고, 문항 유형별 평가 기준을 활용하기 위한 사전 작업입니다.

* 현재 Notebook은 실험 및 검증용 코드이므로, 운영 환경에 바로 적용되는 형태는 아닙니다.
* STT 결과는 음성 품질, 사투리, 잡음, 발화 속도에 따라 달라질 수 있습니다.
* 반응 시간 측정은 주변 소음이나 무음 구간 처리 기준에 영향을 받을 수 있습니다.
* 반복어 비율은 바로 연속된 어절 반복만 계산하므로, 의미상 반복이나 비연속 반복은 반영하지 않습니다.
* 답변 길이 점수는 문항 유형별 휴리스틱 기준이므로, 실제 임상적 기준과는 구분해야 합니다.
* LLM 기반 화행 적절성 평가는 프롬프트 설계와 테스트 케이스에 따라 결과가 달라질 수 있습니다.

### 개선 방향

* 실제 서비스 환경의 음성 데이터로 STT 성능 추가 검증
* 잡음이 있는 음성에서 반응 시간 측정 기준 보완
* 반복어 탐지 기준을 비연속 반복이나 유사 표현까지 확장
* 문항 유형별 답변 길이 기준 재검토
* LLM 평가 프롬프트의 테스트 케이스 확대
* 분석 결과와 실제 사용자 리포트 간 연결 방식 고도화
